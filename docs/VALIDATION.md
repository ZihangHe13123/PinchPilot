## 2026-10-07 Windows 粗粒度时钟

Python 3.13 之前，Windows 上 `time.monotonic()` 和 `time.time()`（包括 `time.time_ns()`）的读数约每 15.6 毫秒才前进一次。CI 使用 Python 3.11，便携包使用 3.12，两处都是这种时钟。由此查出两个问题：一个在产品，一个在测试。

- 相机帧同戳（产品，[Pull Request #4](https://github.com/ZihangHe13123/PinchPilot/pull/4)，提交 5e9ef63）：`CameraWorker.run` 用一次 `time.monotonic()` 读数给每帧打时间戳。某次循环较慢、下一帧已经在缓冲里时，接下来的两次读帧可能落在同一个时钟刻度内，两帧时间戳相同。控制手选择器会把这一帧和下一帧输出为无手；界面取到这两帧时，控制器按设计把后一帧当作重复帧，以 `invalid_or_stale_frame` 停止控制并取消进行中的校准。修复：相机线程丢弃时间戳没有前进的帧，直接读下一帧。看门狗、0.40 秒心跳超时、0.25 秒帧过期和重复帧检查都没有改动，真正重复的帧仍被拒绝。代价是每次同戳少处理一帧；循环启动后第一帧若落在同一刻度内，也会被丢弃。
- 相机帧同戳的验证（macOS 本地与 CI）：端到端回归测试把真实的 `CameraWorker.run` 接到控制器，粗时钟下缓冲帧被丢弃，到达控制器的时间戳严格递增，控制保持开启；去掉这处修复，或把判断从 `<=` 弱化成 `<`，这个测试都失败。把整个测试进程的 `time.monotonic()` 量化到 15.6 毫秒后，全套通过。
- 相机帧同戳尚未在 Windows 真机和真实相机上验证：两帧是否真的会落在同一刻度内、多久一次，取决于真机的循环耗时和相机缓冲行为，目前不清楚。待实测：在已有的 `trial_*.jsonl` 里查原因为 `invalid_or_stale_frame` 的 `control_stopped` 记录和大于 0 的 `discarded_frames`（真正过期的帧也是同一原因，要对照当时的界面轮询间隔）；修复后在真机上回归。合成演示在界面线程用同一时钟打时间戳，同类情况没有处理，只影响演示动画。
- 记录文件重名（测试，[Pull Request #5](https://github.com/ZihangHe13123/PinchPilot/pull/5)，提交 eebd889）：`tests/test_desktop_control.py::test_logging_toggle_and_telemetry_are_local_and_source_labelled` 在 windows-2022 上失败过 1 次，出现在 Pull Request #4 的一次运行里，重跑通过，与该 PR 的改动无关。测试记录的文件名取自 `time.time_ns()`。这个测试在同一个时钟刻度内两次开启记录，第二次得到相同的文件名，产品按设计拒绝覆盖已有文件并提示“无法写入测试记录”，第一份记录保持不变，测试里“应写入新文件”的断言随之失败。界面上只有勾选框能开启记录，启动时也只开启一次，人不可能在 15.6 毫秒内关闭再开启，所以产品没有改动。修复：测试为记录文件名注入逐次递增的时钟读数，并补充断言第二次记录确实开启、没有报错。
- 记录文件重名的验证（macOS）：用临时测试插件把整个测试进程的墙上时钟量化到 15.6 毫秒（部分运行同时量化 `time.monotonic()`），修复前 5 次运行中 3 次失败，失败的都是这一项；修复后 8 次运行全部通过。量化到 1 秒时，修复前全套只有这一项失败，修复后全部通过，说明没有其他测试依赖墙上时钟在两次命名之间前进。临时让新一次记录沿用旧文件，修复后的测试仍然失败。全量测试 696 项通过、5 项跳过。远程检查结果见 Pull Request #5。

## 2026-10-08 多人留一人验证（`ml-pool`、`ml-cv`）

- 改动：新增 `contact_pool.py`（把文件夹里的录制读成一个窗口池）、`contact_cv.py`（留一人验证、按折选择设置、验证表和测试表）、`contact_nets.py`（手指共享 CNN 和通用训练循环），`experiments/contact/` 下每个模型一个起步设置文件。说明见 [MODEL_COMPARISON.md](MODEL_COMPARISON.md) 和 [CONTACT_ML.md](CONTACT_ML.md)。
- 两个 CNN 的前向计算改为矩阵乘法：最后一帧的输出只用到第一层卷积的最后几个位置，两层都可以写成对同一组权重的矩阵乘。`ml-train` 保存的模型结构和权重字段不变。与原来带补零的 `Conv1d` 写法逐一对比，窗口长度1到12帧时双精度下最大差 8.3e-17。在本机上给76,779个窗口打分从约3.3秒降到约0.02秒。
- 自动测试（macOS 本地）：安装 PyTorch 2.14.0 时全量 **739项通过**；模拟未安装 PyTorch 时 **730项通过、9项跳过**；把时钟量化到15.6毫秒后739项通过。Ruff 与93个文件的格式检查通过。
- 测试覆盖的要点：调参阶段的每次训练都不含该折的留出者和验证者；每一折只按自己的验证结果选设置（构造了“全体平均会选错”的例子）；测试阶段每个留出者只打一次分，CNN 的轮数取该折验证选出的平均值；草稿标签、合成数据、不足三人、某人某通道只有一种标签都会被拒绝；阈值搜索与穷举结果一致；共享权重时交换两根手指的输入会交换对应输出，不共享时不会；关闭 `context` 时一根手指的输出不受其他手指影响。
- 规模试跑（合成数据，3人×3场次，每场25,600帧，共230,337个窗口，M 系列 Mac）：首次读入41.8秒，之后读缓存0.3秒；起步设置文件跑完验证的用时为规则1.4秒（3组）、随机森林31秒（3组）、时序CNN 24秒（2组）、手指共享CNN 67秒（3组）；加测试阶段约多20秒。合成数据很容易分开，所有模型的分数都接近1，**这些分数没有意义**，只说明流程和用时。真实数据上随机森林的树会更深，用时可能更长。
- CI 增加一步：在两个平台上安装 PyTorch 后运行 `tests/test_contact_models.py` 和 `tests/test_contact_cv.py`。此前 CNN 相关测试在 CI 上一直是跳过的。
- **尚无真人数据的结果。** 待实测：真实录制上的读入时间和内存占用；Windows 上的用时；三个人的数据是否每人每根手指都有正负样本；按折选出的设置是否稳定。

## 2026-10-08 第一次真人试录与分段录制（v0.15.0）

**第一次真人试录**（v0.14.0 连续计时版本，macOS，一位组员，录到第2轮时手动停止）：

- 录制者的反馈：节奏太快，提示来不及读，更来不及照做。

- 单次捏合只按下一次，单帧噪声不点击，规则闭合/释放阈值滞回。
